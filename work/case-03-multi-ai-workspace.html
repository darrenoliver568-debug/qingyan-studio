PROJECT 03 · AI WORKFLOW / AGENT GOVERNANCE

青砚多 AI 协作工作台 QingYan Multi-AI Collaboration Workspace

Runtime v0.1 · In Validation Evidence-Backed Case Study

我想解决的不是“怎么接更多 AI”，而是“怎么让多个 AI 真正可靠地一起工作”。

最初，我尝试让 ChatGPT 负责规划、WorkBuddy 负责审核、Codex 负责执行。真正运行以后，我发现问题并不在模型能力，而在协作本身：不同 AI 可能读到不同状态、理解不同范围，甚至 Reviewer 也可能基于错误信息做出 PASS。因此，我没有继续增加 Agent，而是把系统收缩成一个最小可验证 Runtime，并在真实项目中持续验证和修正。

01 Scope Control

我先砍掉了一个“看起来很完整”的系统。 01 · SCOPE CONTROL

第一版 AI OS 已经包含 Registry、Router、Dashboard、Lifecycle 等大量模块。独立架构审查指出：核心协作链还没有被验证，系统却已经提前进入复杂治理。我选择暂停继续扩展，把长期 Blueprint 和当前真正能验证的 Runtime 拆开。只保留当前最关键的问题：怎样让规划、审核和执行三个 AI 完成一次真实、可控的协作？这一步让我确认：好的系统设计不只是会加功能，也要知道什么时候做减法。

02 Problem Framing

一次真实故障，让我重新理解了“多 AI 协作”。 02 · PROBLEM FRAMING

Runtime 开始运行后发生了 Directory Drift：执行资产进入了错误位置。更重要的是，我后来发现：独立 Reviewer 本身也不是天然可靠的。如果 Reviewer 读到的不是正确状态，它依然可能认真地得出错误判断。于是我把问题重新定义成：不是“谁来审核谁”，而是“所有 AI 是否基于同一份真实状态工作”。

  • 唯一 Project Root
  • PROJECT.md 作为项目状态入口
  • AI 执行前读取当前状态
  • 找不到关键资产时停止
  • 明确跨 AI 交接规则

Ground Truth before more Agents.

03 AI Workflow

我把“聊天协作”变成了有边界的执行流程。 03 · WORKFLOW DESIGN

把模糊意图、独立审核、执行权限与日志变成一套可运行、可停止、可复核的流程：

Task Brief ↓ Independent Review ↓ Controlled Execution ↓ Execution Log

Task Brief

把聊天中的需求转成明确任务：目标、范围、路径、资产和下一步都写清楚。

Independent Review

方案不能直接执行，必须先被另一个 AI 质疑。

Controlled Execution

PASS 不代表“接着往下做”，只代表允许执行被批准的范围。

Execution Log

不接受一句“做完了”，而是留下可以被下一位 Reviewer 检查的证据。

让每一个 AI 都知道：现在该做什么、不能做什么、做到哪里必须停。

04 Failure Review

真正让我确认这个机制有价值的，是它最后没有 PASS。 04 · FAILURE REVIEW

这套流程随后进入一个真实内部项目运行。执行前：REVISE → 修正 → PASS。执行过程中：Codex 只完成被批准的 Step 1–7，并在下一道 Gate 前停止。但最终 Post-Execution Review 继续检查结果后，仍然给出了：REVISE。

终审发现两处实质性的人工内容重写，说明首次 LLM 输出仍然需要人工改写才能达到要求。

Review Gate 的价值不是保证系统正确，而是让后面的证据依然有机会否定前面的判断。

我更关注的不是“这一次有没有漂亮地全部 PASS”，而是系统有没有能力发现自己其实还没做好。

AI Workflow Design

从“更多 AI”转向“更可靠的协作”。

Project 03 最终让我形成了一套后来持续复用的方法：先运行 → 暴露问题 → 回到真实证据 → 做最小修改 → 再验证。相比“让更多 AI 工作”，我现在更关心的是：怎样让 AI 在真实状态、明确边界和可复核证据下工作。
